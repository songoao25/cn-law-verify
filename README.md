**让 AI 引法先查、照原文、写完自查——中国法律引注核验 MCP。**

CLV（cn-law-verify）是一个核验中国法律法规引注的 MCP 服务，另附一套配套 Skill。它主要不是给人单条查法条用的——主场景是：**你让 AI 写法律分析、起草文书时，AI 自己在写作过程中把法找对、照官方原文引用、写完再自查一遍抓错**，交到你手里的稿子，法条已经是核过的，你不用操心法条的事。

配套 Skill 是给 AI 的规矩层（动笔先查、引用照原文、写完自查），MCP 是能力本体：8 个只读工具，负责找法、取原文和逐字核验。核验不靠模型自觉，靠代码执行：每条引注都回官方源比对——存在性、原文逐字、效力状态，三检缺一不可。

> An MCP server + Skill that makes AI writing about Chinese law look up the right provisions first, quote them verbatim from official sources, and re-check every citation before delivering — existence, verbatim text, and validity status, verified by code, not by the model's memory.

## 它解决什么问题

大模型引用中国法律法规时，最危险的错误不是文风，而是法条本身出错：

- **找不对**：法名记岔、条号记错，或者只记得大概内容、不知道出自哪部法哪一条；
- **引不准**：条文凭记忆默写，漏字、改字、串了别家的条；
- **用错法**：引到的法其实已经废止，还当现行法在用。

没有核验层时，这些错要靠人逐条复查——报一个法名条号、调回原文、自己一个字一个字对。CLV 把这件事交给代码：AI 找法时有简称与错别字纠错、按内容反查；引用时直接取官方原文填入；写完后整段引注自动过一遍核验，错在哪儿当场标出来。

## 怎么用

### 主路径：发给你的 AI 助手，一步接上

国产 agent 已经适配好了。不用装环境、不用配代码：

1. 复制本仓库链接 `https://github.com/songoao25/cn-law-verify`；
2. 发给你的 AI 助手——WorkBuddy、Kimi、豆包等都行，它自己会下载、接上；
3. 接上之后，照常让 AI 写分析、起草文书，核验在写作过程中自动发生。

配套的 [SKILL.md](SKILL.md) 会随仓库一同被 agent 读到，它给 AI 定的规矩是：先查后引、引用照官方原文并带效力状态与官方链接、查不到就明说、发现已废止必须点名排除。

### 次路径：在支持 MCP 的客户端里手动配置

零依赖，只需要 Python 3.10+：

```bash
git clone https://github.com/songoao25/cn-law-verify.git
cd cn-law-verify
python3 server/cn_law_verify_server.py --version
```

stdio 方式注册（仓库根目录已附 `.mcp.json` 示例）：

```json
{
  "mcpServers": {
    "cn-law-verify": {
      "command": "python3",
      "args": ["server/cn_law_verify_server.py"]
    }
  }
}
```

或以 Streamable HTTP 方式启动（同一核验内核，适合只收远程 server 的客户端；默认只绑 127.0.0.1，对外托管请置于反向代理之后）：

```bash
python3 server/cn_law_verify_server.py --http --port 8765
# 端点：POST http://127.0.0.1:8765/mcp
```

仓库自带条文级快照库（`data/snapshot.db`，见下文「它怎么工作」），`get_article` / `search_articles` 开箱即走快照通道；删除该文件则自动回退官方实时通道。

### 单条查

不接 AI 也能用：查一部法在不在、是不是现行有效，查某一条的官方原文是什么——用 `lookup` 一句话直达即可（见下文工具表）。

## 八个工具

全部工具只读（`readOnlyHint: true`），每次返回都带数据来源与取数时间。参数类型错误只返回人话工具错误、绝不打崩进程；错误信息说清哪一步、什么问题、下一步怎么办。

| 工具 | 说明 |
|---|---|
| `lookup` | 一句话直达（「民法典577条」「劳动合同法第三十九条是什么」）：解析法名＋条号与常用简称；法名有一两字之差（错别字）且三路解析全部落空时，按已知法名全集做确定性近名纠错（编辑距离＋拼音距离两级判别），纠正必显式标注、并列则返回候选清单。此纠错仅 lookup 提供，核验类工具对写错的法名不纠错、只报错 |
| `flk_search` | 三库实时检索法规（`source`：auto 三库合并／flk 国家法律法规数据库／moj 司法部行政法规库／gzk 国家规章库），返回效力状态、官方链接与所属库标记 |
| `get_law` | 单部法规元数据＋章节目录大纲＋版本沿革（官方详情页实时数据） |
| `get_article` | 单条条文逐字原文：快照库优先（注明快照时间），未收录走官方实时通道 |
| `search_articles` | 跨法规条文级检索：快照库为主并注明覆盖范围；未命中走官方正文检索兜底（仅前 5 部候选、明示非全库检索） |
| `verify_citation` | 核验一条引注：法名＋条号（＋可选引文）→ 存在性／效力／原文逐字三检结论；flk 未收录时自动转 moj 条级三检、再转 gzk 存在性（效力未核、结论封顶 exists_only）；实时通道故障时自动降级本地快照并标注 |
| `check_citations_in_text` | 整段文本抽取全部《法名》第N条引注，逐条三检（含引文与官方原文逐字比对，未抽到引文的条目会明说只验了存在性与效力），返回逐条结论＋汇总＋问题清单（单次上限 20 条）。只认带《》书名号的引注，裸写的「法名第N条」不抽取（见「已知边界」第 9 条） |
| `check_support` | 蕴含初筛：判断引注是否大体支持论断。词面启发式（关键词覆盖／数字一致性／极性冲突／排他性限定／条件偷换／单位偷换／主体偷换／数量边界方向／多档分档锚定九类信号），四档结论＋逐条理由；是初筛，**不替代人工判断**，输出恒带此说明 |

核验结论恒为三态：**已核验**（verified）／**仅确认存在**（exists_only，效力或比对有保留并写明）／**未通过核验**（not_verified）。

## 它怎么工作

CLV 一共五层：

1. **本地法规快照库**——自己存的法规全文与效力状态，是比对时的标准答案。当前已入库 **869 部、44,153 条**（SQLite，`data/snapshot.db`，由 `tools/build_snapshot.py` 从官方 DOCX 离线切条建成，串行限速、断点续传）；国家层面现行有效法规总清单 1,837 部，仍在持续扩建，未入库部分由实时通道覆盖，保鲜走增量更新（`tools/update_snapshot.py`：逐部比对官方元数据，只有变化的法规才整部重建，结果追加写入 `data/update_log.jsonl`）。
2. **双通道取数**——先查本地快照；快照里没有、或者要确认最新效力的，再走官方实时接口现查。两路互相兜底：断网能用，官方接口改版也不至于全盘失效。结论恒标注所依据的通道与时间，绝不静默用旧数据冒充实时结果。
3. **核验引擎**——引注进来先做文本规范化（标点、全半角、空白统一），再与官方原文逐字比对，最后分类判定：对得上／条号对但文不对／原文被改（漂移）／串了别家的条／已废止／根本不存在（编造）。整段核验先从文稿里抽出全部《法名》第N条，再逐条过这个引擎。
4. **定位纠错层**——负责「找得到」：法名与关键词检索、按条号精确取原文、按内容反查条文；外加简称映射与错别字近名纠错，写错一两个字也能定位到正名。
5. **接口层**——上面四层的能力打包成 8 个工具，经 MCP 协议（stdio 与 Streamable HTTP 双传输）对外，任何支持 MCP 的 agent 接上就能调；配套 Skill 是规矩层，教 agent 何时查、怎么引、如何读核验结果。

实时通道按三库分工：

| 库 | 管什么 | 能做到哪一步 |
|---|---|---|
| 国家法律法规数据库（flk.npc.gov.cn） | 法律、行政法规、司法解释等主干 | 存在性＋效力＋条文原文逐字三检（主通道） |
| 司法部国家行政法规库（xzfg.moj.gov.cn） | 行政法规（flk 未收录时兜底） | 详情页全文可做条级三检；其检索端点当前不按关键词过滤（2026-11-23 实测），改走本地标题索引（`data/moj_index.json`，分页遍历全库含同名历史版本）：标题检索覆盖全库、精确标题直达详情页，效力与原文仍以详情页实时取数为准。索引自带构建时间，超过 30 天未重建时检索结果会标注索引可能过期；重建命令 `python3 tools/build_moj_index.py` |
| 国家规章库（gov.cn 规章库） | 部门规章、地方政府规章 | 只有元数据＋摘要：只做存在性，无官方效力字段、无条文全文，效力恒标「未核」、核验结论封顶 exists_only |

健康检查：`python3 server/cn_law_verify_server.py --health`，输出快照概况与三库通道探活结果（JSON），供运维巡检。

设计细节（经验继承表、缺点解法表、数据源与版本策略）见 [docs/DESIGN.md](docs/DESIGN.md)。

### 核验示例

`verify_citation` 入参：

```json
{"law": "中华人民共和国民法典", "article": "第五百七十七条",
 "citation_text": "当事人一方不履行合同义务或者履行合同义务不符合约定的，应当承担继续履行、采取补救措施或者赔偿损失等违约责任。"}
```

返回要点：法规定位（官方标识与详情页链接）、效力状态「有效」、官方原文整条截取、逐字比对 `exact_match: true`、总判定 `verdict: "verified"`。法名不存在、条号漂移、法规已废止、引文改字，都会被分别指出并给出 `not_verified`——而不是含糊地「仅供参考」。

## 实测成绩

以下数字来自 2026-11-24 的密封闭卷评测，口径先说清：**题集事先对被测方不可见，真值来自独立于本工具的官方源归档，判定规则跑前冻结，五个同类工具各自独立进程串行跑、无并发负载**。同场对照的还有 flk-mcp 等四个同类项目。

| 项目 | CLV 成绩 |
|---|---|
| 核心六类核验（引注属实／文不对版／条号漂移／编造／串法／已废止，共 2,000 题） | **1986 / 2000（99.3%）** |
| 其中：引注属实 598/600、文不对版 399/400、条号漂移 298/300、编造 300/300、串法 200/200、已废止 191/200 | |
| 法名定位（200 题） | 175 / 200（87.5%） |
| 条号定位（170 题） | 146 / 170（85.9%） |
| 整段核验的引注抽取（358 条） | 342 条抽出，其中判定正确 338 条 |
| 时延（串行单测） | p50 8.76 秒／p95 19.32 秒，由官方源往返主导 |

如实标注的短板：

- **找对不如验得准**：定位环节八成多，核验环节接近满分——第一次找错时，靠写完后的整段自查能兜回一部分；
- **少数小众法规的废止状态未标全**：已废止类失分的 9 题集中在 3 部小众法规上，是当前唯一成片短板，快照扩建中在补；
- **简称与错别字定位仍在提升**：个别简称（如《网安法》的部分问法）尚未解析出来；
- **`check_support` 是启发式初筛**：严格四档口径下 60 题对 19 题，它的设计定位就是初筛，恒标注「不替代人工判断」，重要文稿的蕴含判断请人工读条文全文。

仓库内 `eval/` 另附 200 题开发集（真引注 80／文本错位 40／条号漂移 30／编造法名 20／简称 15／已废止 10／跨法错配 5），生成器 `eval/generate_cases.py`、运行器 `eval/run_eval.py`、成绩 `eval/RESULTS.md` 随仓交付；0.5.2 在该开发集上复跑 200/200——这是开发集回归口径，不与上面的闭卷成绩混读。

## 已知边界

以下条目经多轮实测确认，是当前版本的真实边界，不隐藏、不夸大：

1. **`check_support` 是词面启发式，不是语义判定**（结构性上限）：论断把多档条文中的某一档情形整段丢弃、只摘述另一档时，词面信号无法与「只摘述加重档」可靠区分，这类「引对了条、摘错了档」的漏检无法靠词面方法根除。重要文稿的蕴含判断必须人工读条文全文。
2. **整段核验的引文关联有盲区**：引文与引注之间隔着完整句子（跨句引用）时不做关联（只验存在性与效力、会明说）；无引号的转述性引用同样不抽引文。引文紧邻引注之前或之后可正常关联。
3. **快照降级通道不给条号沿革建议**：实时通道不可用、走快照兜底时，条号不存在只给通用提示，不提供「旧条号可能迁往哪条」的线索（快照库只存现行一版，存版本沿革需成倍扩库，裁决不做，降级场景以可用性优先）。
4. **快照扩建未完成**：国家层面总清单 1,837 部，已入库 869 部；未入库法规走实时通道核验不受影响。决定／决议／法律解释类无条级结构文件不会入快照库（约占清单 9.8%），其核验恒走实时通道。
5. **moj 标题索引会过期**：索引是离线快照，超 30 天未重建时检索结果会标注；新公布的行政法规在重建前只能靠 flk 主通道与详情页直达覆盖。
6. **gzk 规章通道只验存在性**：无官方效力字段与条文全文，结论封顶 exists_only、效力恒标未核——这是数据源本身的边界，不是实现缺陷。
7. **时延**：核验时延由官方源往返主导（整段核验按引注条数累加），批量文稿请预留时间，不要按本地工具的时延预期使用。
8. **lookup 近名纠错有边界**：只覆盖法名差一两字的错别字，候选集限于快照库、flk 枚举清单与 moj 标题索引中已知的法名（gzk 规章无本地名录、不在候选内）；编辑距离与拼音距离都分不出唯一胜者时只返回候选清单、不代为决定；任一解析通道报错（网络异常等）时不触发纠错、按原口径报错。纠错只发生在 lookup——`verify_citation` 等核验工具对写错的法名仍判未通过，不因纠错而放行编造或写错的引注。
9. **整段核验只认带《》书名号的引注**（0.5.2 起）：`check_citations_in_text` 只抽取写成《法名》第N条的引注；文中不带书名号、直接裸写的「法名第N条」（如「根据民法典第五百七十七条」）不会被抽出来，也就不会被核验——哪怕它写错了、甚至是编造的，本工具也不会报错提示。整段交付前若要不漏检，请把引注都写成《》格式，或对裸写的引注逐条用 `verify_citation` 单独核验。

## 安全与数据口径

- 数据只来自官方源：请求只发往白名单官方域名、全程 HTTPS 并开启 TLS 证书校验，下载跳转逐跳复检域名；遇官方验证页立即终止。
- server 无写工具、不留存查询内容；本地 stdio 模式下，核验只把法名与条号发往官方源，待核验文本不出本机。**托管模式下**文本会到达 server 运营方，请知情选择部署方式。
- 法规文本源自国家法律法规数据库（flk.npc.gov.cn）公开数据；该库无公开 API，本项目使用其公开前端接口，并遵守「不批量抓取」的边界（快照数据经官方下载通道＋人工确认更新）。

## 与 flk-mcp 的关系

CLV 是在 flk-mcp 的基础之上做的：flk-mcp 能查的，CLV 全都能查——检索法规、取整部法、取单条原文，功能上是超集。差别在查完之后：flk-mcp 把原文交回来，对不对由看的人自己判；CLV 多了一层代码判定，直接给出结论，并多了整段批量核验与简称、错别字纠错。取数方式也不同：flk-mcp 在线现查官方库，CLV 是本地快照＋官方实时双通道。
