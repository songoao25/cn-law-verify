# cn-law-verify

**给 AI 的中国法条核验层：查得到、验得真、带效力与出处。**

一个面向多 Agent 通用的 MCP server ＋配套 Skill。大模型引用中国法律法规
时最危险的错误不是文风，而是**编造法条、引错条号、拿已废止的旧条文当
现行法**。cn-law-verify 把核验从「靠模型自觉」变成「靠代码执行」：
引文写入输出之前，先向国家法律法规数据库官方源逐条核验——
存在性、原文逐字、效力状态，三检缺一不可。

> An MCP server + Skill that verifies Chinese legal citations against the
> official National Laws and Regulations Database: existence, verbatim
> text, and validity status — checked by code, not by the model's memory.

## 快速开始

零依赖，只需要 Python 3.10+：

```bash
git clone https://github.com/songoao25/cn-law-verify.git
cd cn-law-verify
python3 server/cn_law_verify_server.py --version
```

在 MCP 客户端中注册（stdio）。仓库根目录已附 `.mcp.json` 示例：

```json
{
  "mcpServers": {
    "cn-law-verify": {
      "command": "python3",
      "args": ["server/cn_law_verify_server.py"]
    }
  }
}
```

或以 Streamable HTTP 方式启动（同一核验内核，适合只收远程
server 的客户端；默认只绑 127.0.0.1，对外托管请置于反向代理之后）：

```bash
python3 server/cn_law_verify_server.py --http --port 8765
# 端点：POST http://127.0.0.1:8765/mcp
```

仓库自带条文级快照库（`data/snapshot.db`，见下文「快照库」），
`get_article` / `search_articles` 开箱即走快照通道；删除该文件则
自动回退官方实时通道。

配套规矩层见 [SKILL.md](SKILL.md)：先查后引、引用必带效力状态与官方
链接、查不到就明说、发现废止必须点名排除。

## 工具

| 工具 | 说明 | 状态 |
|---|---|---|
| `flk_search` | 三库实时检索法规（`source`：auto 三库合并／flk 国家法律法规数据库／moj 司法部行政法规库／gzk 国家规章库），返回效力状态、官方链接与所属库标记 | ✅ 可用 |
| `verify_citation` | 核验一条引注：法名＋条号（＋可选引文）→ 存在性／效力／原文逐字三检结论；flk 未收录时自动转 moj 条级三检、再转 gzk 存在性（效力未核、结论封顶 exists_only）；实时通道故障时自动降级本地快照并标注 | ✅ 可用 |
| `get_law` | 单部法规元数据＋章节目录大纲＋版本沿革（官方详情页实时数据） | ✅ 可用 |
| `get_article` | 单条条文逐字原文：快照库优先（注明快照时间），未收录走官方实时通道 | ✅ 可用 |
| `search_articles` | 跨法规条文级检索：快照库为主并注明覆盖范围；未命中走官方正文检索兜底（仅前 5 部候选、明示非全库检索） | ✅ 可用 |
| `check_citations_in_text` | 整段文本抽取全部《法名》第N条引注，逐条三检（含引文与官方原文逐字比对，未抽到引文的条目会明说只验了存在性与效力），返回逐条结论＋汇总＋问题清单（单次上限 20 条） | ✅ 可用 |
| `lookup` | 一句话直达（「民法典577条」「劳动合同法第三十九条是什么」）：解析法名＋条号与常用简称，输出机器结论／人工复核清单两段式结果；法名有一两字之差（错别字）且三路解析全部落空时，按已知法名全集做确定性近名纠错（编辑距离＋拼音距离两级判别），纠正必显式标注、并列则返回候选清单——此纠错仅 lookup 提供，核验类工具对写错的法名不纠错、只报错 | ✅ 可用 |
| `check_support` | 蕴含初筛：判断引注是否大体支持论断。**词面启发式 v3.1**（关键词覆盖／数字一致性／极性冲突／排他性限定／条件偷换／单位偷换／主体偷换／数量边界方向／多档分档锚定九类信号），四档结论＋逐条理由；是初筛，**不能替代人工判断**，输出恒带此说明。已知盲区见下文「已知盲区」 | ✅ 可用（启发式） |

全部工具只读（`readOnlyHint: true`），每次返回都带数据来源与取数时间。
参数类型错误只返回人话工具错误、绝不打崩进程；错误信息说清哪一步、
什么问题、下一步怎么办。

## 三库分工

| 库 | 管什么 | 能做到哪一步 |
|---|---|---|
| 国家法律法规数据库（flk.npc.gov.cn） | 法律、行政法规、司法解释等主干 | 存在性＋效力＋条文原文逐字三检（主通道） |
| 司法部国家行政法规库（xzfg.moj.gov.cn） | 行政法规（flk 未收录时兜底） | 详情页全文可做条级三检；**其检索端点当前不按关键词过滤（2026-11-23 实测），859 起改走本地标题索引（`data/moj_index.json`，分页遍历全库 1,189 行含同名历史版本，官方现行有效口径 603 部）：标题检索覆盖全库、精确标题直达详情页，效力与原文仍以详情页实时取数为准。索引自带构建时间（`built_at`），超过 30 天未重建时检索结果会标注索引可能过期；重建命令 `python3 tools/build_moj_index.py`** |
| 国家规章库（gov.cn 规章库） | 部门规章、地方政府规章 | 只有元数据＋摘要：只做存在性，**无官方效力字段、无条文全文**，效力恒标「未核」、核验结论封顶 exists_only |

健康检查：`python3 server/cn_law_verify_server.py --health`
输出快照概况与三库通道探活结果（JSON），供运维巡检。

### verify_citation 示例

入参：`{"law": "中华人民共和国民法典", "article": "第五百七十七条",
"citation_text": "当事人一方不履行合同义务或者履行合同义务不符合约定的，
应当承担继续履行、采取补救措施或者赔偿损失等违约责任。"}`

返回要点：法规定位（官方 `bbbs` 与详情页链接）、效力状态「有效」、
官方原文整条截取、逐字比对 `exact_match: true`、总判定
`verdict: "verified"`。法名不存在、条号漂移、法规已废止、引文改字，
都会被分别指出并给出 `not_verified`——而不是含糊地「仅供参考」。

核验结论恒为三态：**已核验**（verified）／**仅确认存在**
（exists_only，效力或比对有保留并写明）／**未通过核验**
（not_verified）。

## 它和同类项目的关系

- 「查得到原文」的检索型项目已经不少；本项目的差异在**核验**：
  第一个把「引文抽取 → 逐条回官方源比对 → 三态结论」做成确定性
  代码管线，并配公开测试与 200 题评测集（eval/）。
- 数据策略是**快照库＋实时复核双通道**：本地快照保证稳定可复现，
  实时通道复核最新效力；结论恒标注所依据的通道与时间，绝不静默
  用旧数据冒充实时结果。
- 设计细节（经验继承表、缺点解法表、数据源与版本策略）见
  [docs/DESIGN.md](docs/DESIGN.md)。

## 安全与数据口径

- 数据只来自官方源：请求只发往白名单官方域名、全程 HTTPS 并开启
  TLS 证书校验，下载跳转逐跳复检域名；遇官方验证页立即终止。
- server 无写工具、不留存查询内容；本地 stdio 模式下，核验只把
  法名与条号发往官方源，待核验文本不出本机。**托管模式下**文本会
  到达 server 运营方，请知情选择部署方式。
- 法规文本源自国家法律法规数据库（flk.npc.gov.cn）公开数据；
  该库无公开 API，本项目使用其公开前端接口，并遵守「不批量抓取」
  的边界（快照数据经官方下载通道＋人工确认更新）。

## 已知盲区（860 终审定版，使用者请知情）

以下条目经三轮实测确认，是当前版本的真实边界，不隐藏、不夸大：

1. **`check_support` 是词面启发式，不是语义判定**（结构性上限）：
   论断把多档条文中的某一档情形**整段丢弃**、只摘述另一档时，
   词面信号无法与「只摘述加重档」可靠区分，这类「引对了条、
   摘错了档」的漏检无法靠词面方法根除；语义级对齐与本项目
   「零依赖、诚实标注初筛」的定位冲突，终审裁决不做。重要
   文稿的蕴含判断必须人工读条文全文。
2. **整段核验的引文关联有盲区**：引文与引注之间隔着完整句子
   （跨句引用）时不做关联（只验存在性与效力、会明说）；无引号
   的转述性引用同样不抽引文。引文紧邻引注之前或之后可正常关联。
3. **快照降级通道不给条号沿革建议**：实时通道不可用、走快照
   兜底时，条号不存在只给通用提示，不提供「旧条号可能迁往
   哪条」的 renumber 线索（快照库只存现行一版，存版本沿革
   需成倍扩库，终审裁决不做，降级场景以可用性优先）。
4. **快照扩建未完成**：国家层面清单已处理约 15.6%（860 时点），
   未入库法规走实时通道核验不受影响；决定／决议／法律解释类
   无条级结构文件不会入快照库（约占清单 9.8%），其核验恒走
   实时通道。
5. **moj 标题索引会过期**：索引是离线快照，超 30 天未重建时
   检索结果会标注；新公布的行政法规在重建前只能靠 flk 主通道
   与详情页直达覆盖。
6. **gzk 规章通道只验存在性**：无官方效力字段与条文全文，
   结论封顶 exists_only、效力恒标未核——这是数据源本身的
   边界，不是实现缺陷。
7. **时延**：核验时延由官方源往返主导（860 实测：5 路并发
   单条核验 9.6–15.9 秒；12 条引注整段核验约 68 秒），批量
   文稿请预留时间，不要按本地工具的时延预期使用。
8. **lookup 近名纠错有边界**（0.5.1 新增，843b）：只覆盖法名
   差一两字的错别字，候选集限于快照库、flk 枚举清单与 moj
   标题索引中已知的法名（gzk 规章无本地名录、不在候选内）；
   编辑距离与拼音距离都分不出唯一胜者时只返回候选清单、
   不代为决定；拼音表按常用读音静态生成，多音字读音差异
   可能使同音破并列失效、退回候选清单；任一解析通道报错
   （网络异常等）时不触发纠错、按原口径报错。纠错只发生在
   lookup——`verify_citation` 等核验工具对写错的法名仍判
   未核实，不因纠错而放行编造或写错的引注。
